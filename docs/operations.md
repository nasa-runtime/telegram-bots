# 运维与故障语义

## 观察目录是否生效

`/readyz` 反映当前服务可用性。无效候选保持上一份有效目录，因此还应检查 `GET /api/config/status` 和下列指标：

| 指标 | 含义 |
| --- | --- |
| `telegram_catalog_desired_generation` | 最近读取到的合法代号；无法解析或越界时为 0 |
| `telegram_catalog_applied_generation` | 当前有效代号 |
| `telegram_catalog_last_success_seconds` | 最近一次目录发布的 Unix 秒 |
| `telegram_catalog_last_check_seconds` | 最近一次对账完成或超时的 Unix 秒 |
| `telegram_catalog_rejected` | 最近候选是否处于拒绝状态，0 或 1 |
| `telegram_catalog_rejected_total` | 拒绝次数；持续无效的文件会反复累计 |
| `telegram_catalog_draining_bots` | 已移除且仍未退出的消费域数量 |
| `telegram_bot_accepted_total{bot}` | 当前消费域累计受理数 |
| `telegram_bot_deliveries_total{bot,outcome}` | 当前消费域的 sent、failed、unknown、dropped 数量 |
| `telegram_messages_total{outcome}` | 跨目录保留的进程累计 accepted、sent、failed、unknown、dropped 数量 |

机器人移除后，其逐 bot 样本会消失；重新加入会建立新消费域计数。轮换同一身份时复用计数；别名变化会改变标签。跨目录连续统计应使用进程级 `telegram_messages_total`。所有计数重启后清零。

候选连续两轮一致前可能出现 desired/applied 短暂不同。超过 10 秒仍不同，或 `telegram_catalog_rejected=1`，应查看控制面中的固定拒绝摘要。只有 `last_success_seconds` 很旧不代表异常：配置长期不变时不会重复发布，应检查 `last_check_seconds`。

## 日常变更

1. 基于当前已应用目录生成完整新文件，递增 `generation`。
2. 凭据变化时先生成新文件与原始字节 SHA-256，在目录中写入准确路径和摘要。
3. 多文件导入的所有实际文件使用同一个代号；先准备完整内容，再切换文件或目录符号链接。
4. 观察 applied 代号达到目标值，且拒绝状态已清除。不要只检查文件更新时间或 readiness。

目录文件先到、secret 后到，或相反，都可能短暂被拒绝；它们匹配后自动生效。部分材料变化不会先应用权限或目的地。

恢复先前配置时，以更大的代号提交旧业务内容。不要把旧代号重新覆盖到当前文件，否则运行中的实例会拒绝倒退。启动时的代号基线来自挂载文件，进程重启不保存防倒退记录。

## 移除、轮换与紧急撤销

移除 bot 时同时删除各调用方对它的引用；否则整个候选被拒绝。允许保留 `allowed_bots: []` 的调用方用于读取空目录和服务配置状态。全部 bot 和调用方都可以为空。

新目录发布后，旧凭据的新请求返回 401；使用旧代完成认证但仍在上传的请求入队时返回 503。已受理消息使用受理时的材料与目标继续处理，不会被重写为新目标。

移除后的排空最多等待 `dispatcher.shutdown_timeout_ms`。等待过程中同一 Telegram 身份不能重新加入；候选自动重试，消费域退出后即可生效。此前已受理消息可能仍使用旧 token。遇到材料泄露时，先在 Telegram 撤销 token，并停止受影响服务；仅从目录移除不能撤销已经发出的网络请求。

## 常见拒绝

| 现象 | 检查与处理 |
| --- | --- |
| 必需目录不存在，进程启动失败 | 核对目录挂载与绝对路径；不使用镜像内目录兜底 |
| 凭据摘要不一致 | 对文件原始字节计算 SHA-256，注意末尾换行；确认容器实际挂载内容 |
| generation 不一致或越界 | 多个导入文件必须属于同一次完整部署，代号范围为 1..=9007199254740991 |
| 相同代号改变内容 | 增加代号；有效目录不会就地修改 |
| 引导配置改变 | 恢复原引导文件，或安排重启；不要在运行期改 listener、来源或 profile |
| HTTP 或停机预算改变 | 安排重启，以新预算启动 |
| 机器人仍在排空 | 等待排空或超时退出；不要启动另一个活动实例绕过该门禁 |
| 读取超时 | 辅助进程被终止回收后自动重读，旧目录继续运行；检查挂载或文件系统 |
| 读取进程无法回收 | 服务失败停机，不追加读取进程；检查内核 I/O、挂载与节点，再由平台恢复实例 |
| 202 很快但没有通知 | 查看 failed/unknown/dropped 与平台权限；202 不是投递回执 |
| 429 | 区分 HTTP 入队过载和后台 Telegram 限流；扩大队列不能提高平台允许速率 |

## 发送与停机

服务不自动重发。明确失败、结果未知和丢弃都需要业务方结合通知用途处理；没有可查询的消息流水。不要根据 `unknown` 自动补发，否则可能重复通知。

正常停机使用 SIGTERM 或 SIGINT。平台终止期限应大于应用预算；默认建议至少 70 秒。所有队列并行排空，共享全局截止时刻，不按 bot 数量逐个累加等待。停机日志记录累计 dropped/unknown；强制退出或节点故障可能来不及输出最终指标。

单实例队列只在内存中存活，重启没有重放。对持久可靠投递有要求的业务应在上游使用持久任务或消息系统，并自行确定幂等与结果未知处理策略。
